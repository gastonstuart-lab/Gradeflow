### Canonical and legacy storage

Let C=classId, I=gradeItemId, U=authenticated userId. Firestore class base is `users/U/classes/C`.

| Data | Local canonical key | Legacy fallback | Firestore path / document ID |
| --- | --- | --- | --- |
| Classes | `classes` | none | `users/U/classes/C` |
| Roster | `students_C` | `students`, filter classId | class base `/students/{studentId}` |
| Items | `grade_items_C` | `grade_items`, filter classId | class base `/gradeItems/I` |
| Scores | `scores_C_I` | `student_scores`, filter **only item ID** | class base `/gradeItems/I/scores/{studentId}` |
| Categories | `categories_C` | `grading_categories`, filter classId | class base `/categories/{categoryId}` |
| Exams | `exams_C` | `final_exams`, filter current roster IDs | class base `/exams/{studentId}` |
| Undo history | `change_history_C` | `change_history`, accepts null classId or matching class | class base `/scoreHistory/{changeId}` |
| Templates | `grading_templates` | none | `users/U/templates/{templateId}` |
| Seating layouts | `seating_layouts_C` | none | class base `/seatingLayouts/{layoutId}` |
| Seating selection/room | `seating_active_layout_C`, `seating_room_setup_C` | none | class base `/seatingMeta/default`, activeLayoutId/roomSetupId |
| Shared room setup | `room_setups` | none | `users/U/roomSetups/{roomSetupId}` |

Local canonical keys, including an encoded empty list, take precedence over legacy. Score fallback cannot prove class ownership without a validated item join. Exam fallback depends on today's roster, so students removed earlier cannot be reliably recovered by that reader alone. Raw legacy records must be preserved and ambiguities reported, not guessed. Local academic keys are not account scoped.

Local saves replace entire lists. Firestore saves set each submitted document, **do not delete omitted documents** and use unchunked batches; student deletion has an explicit delete but score/exam list removals do not. `deleteGradeItem` only deletes its cloud parent doc, leaving score children; class cascade separately enumerates children and deletes them. Cloud class deletion removes students, items/scores, history, exams, categories, seating/meta and finally class; it is non-atomic and unpaged. Local class deletion removes scoped data and known item score keys but leaves global legacy lists, allowing fallback resurrection. `LocalRepository.clearAll` clears all preferences; Firestore clearAll is unsupported.

Adjacent preservation scope: `ClassScheduleService` stores `class_schedule_v1:U:C` with fallback/adoption from `class_schedule_v1:C`; `ClassNoteService` uses `class_notes_v1:U:C`. These remain local even with the core Firestore repository. `DashboardPreferencesService` scopes supplied base keys by user and has one-time legacy adoption. Other shell/tool preferences are not all owned by DataRepository; backup must enumerate actual local key/type/value inventory, not assume a Firestore export includes settings. Period creation must not rewrite any of these keys or class/roster/seating records.

### Calculation and actual Excel routes

`CalculationService.calculateStudentGrades` filters scores per student; an absent assessment row means 100%, an explicit null is excluded; raw/maxScore ×100 normalization precedes average/sum/bestN/dropLowestN. Active category weights are renormalized over non-null categories. Final grade is process×0.40 + exam×0.60 and is null if either input missing. Sum can exceed 100. Preserve these semantics even if a later grading policy changes. Invalid maxima/N/weights need explicit validation; do not silently repair historical inputs. `ensureDefaultScoresForGradeItem` defaults `fillNulls: true`, which can replace deliberate clears; adoption must not call it.

Actual XLSX callers are in `ExportScreen`, not GradebookScreen:

* `_calculateGrades` loads active class roster/categories/items, all item scores and current-roster exams, then computes grades. `_exportPerClass` and `_exportPerStudent` call `ExportService.generateXlsx`. It emits student ID, Chinese/English names, category columns, Process Score (40%), Exam Score (60%), Final Grade; all are text cells, scores fixed to two decimals, null blank. It has no individual assessment columns or period label.
* `_buildAllClassesExportDataset` independently reads repository data for `ClassService.classes`, which includes archived classes; it unions category names and maps names back to IDs, so duplicate names within one class can collapse. `_exportAllClasses` builds its workbook directly with Excel, adding class/subject/year/term fields. It bypasses `generateXlsx`.
* `_exportClassDetails` is PDF-only. Seating export is unrelated. No focused existing XLSX/repository test file was found under `test/`.

Historical exports need a single frozen dataset adapter used by both Excel routes; no live roster/category/exam lookup and no shared mutable service caches. Preserve current summary cells/types/rounding/order. Add period-labelled filename and metadata sheet (and an optional assessment-detail sheet) without replacing the summary contract. Compare decoded cell values/types, not XLSX ZIP bytes. All-class history must select periods explicitly, not infer from today's class.term or union duplicate labels without IDs.

## Recommended additive model (proposal only)

Keep existing class ID, roster, seating, schedules, notes and settings. Introduce an independent academic control document `users/U/gradebooks/C` with `activePeriodId`, monotonically increasing epoch, schemaVersion, revision, lifecycle and rollover operation reference. Keep this outside Class serialization: old `saveClasses().set()` otherwise erases added fields. Periods live at `users/U/gradebooks/C/periods/P`, independent of the deletable class subtree.

Each period has a stable random ID, label/year/term, owner/class IDs, creation/close timestamps, predecessor, template/policy version and state (`preparing`, `active`, `closing`, `sealed`). Under it store category documents, assessment documents with score children, exams by student, and a period-scoped history ledger. All writes require explicit period and expected epoch/revision, not a silently looked-up current period. Exactly the control's activePeriodId is writable; states alone cannot create two active periods.

At close, freeze export roster labels/order (student IDs/names/seat/class code; no photos required), historical class labels, complete category/item metadata and active flags, all score rows including nulls and timestamps, exams including explicit missing state, calculation policy version, and materialized category/process/final results. Store a manifest of document IDs, counts, per-chunk hashes and root digest, ordered export columns, schema/source revision and operation ID. The sealed dataset is self-contained: future edits/deletions of live students, labels, weights or templates cannot affect historical calculation or export. Preserve raw legacy backup separately, including records the current readers exclude. Corrections to a sealed period create an explicit superseding revision with audit link; never mutate the original.

New periods automatically materialize exactly **20 editable assessments**: Quiz 1–2, Classwork 1–6, Homework 1–6, Participation 1–6. Use stable category role IDs rather than matching translated/display names. Deterministic IDs derived from operation/role/ordinal make retry safe. Names, maximum scores, category association and active status remain teacher-editable under normal validation; adding more assessments is allowed, particularly participation. The counts are creation defaults, not a permanent cap or a reseeding rule after teacher deletion. Default maxScore=100, four category weights=25%/average for a fresh template; preview any teacher-selected weight template without changing prior periods. Version this template. Start with no copied old scores/exams; missing scores retain the established 100% policy, explicit clears stay null. Do not run demo seeds or render-time auto-seeds on archives. UI validation/editability is still an acceptance gate; fixture proves only existing local service can persist all 20 edits.

### Adoption alternatives

| Option | Benefit | Problem / decision |
| --- | --- | --- |
| Add periodId fields throughout legacy records and bulk migrate | Uniform query later | Destructive exposure to old-client list saves, unscoped local data and exam identity; large copy and rollback surface. Reject for first slice. |
| Infer a period from class.term without copying | Minimal initial writes | Term is mutable; no frozen roster/weights/exams, stale clients mutate history. Reject. |
| Per-class lazy, explicit adoption into additive namespace | Preserve originals; bound verification to one chosen class | Recommended, with backup, ownership resolution, write fence and verified copy before activation. Not a lazy fallback on every read. |

Classes without a control remain on the unchanged legacy reader/writer. Before adopting one class, resolve canonical/legacy provenance and account ownership; stage the complete existing gradebook as its initial active period, preserving IDs/values/nulls/inactive rows and current calculation results. Do not seed or normalize it. Keep legacy data untouched, with provenance in the manifest. Once verification succeeds, atomically switch the control and fence legacy academic writes. The next rollover seals this period and creates the 20 defaults. Do not use MigrationService, delete source lists, or auto-adopt unowned local data on sign-in. Existing ambiguous legacy data may require human ownership reconciliation before adoption, without reading real data in this PR.

### Ordering, concurrency and interruption

1. Capture authenticated owner/backend/class/epoch; reject account/context change. Flush service queues with explicit error results and await cloud acknowledgement. Require online server-source checks for cloud adoption/rollover. A stale cache cannot assert readiness. Local mode requires exclusive origin/account/class lock; if safe multi-tab exclusion/durable storage is unavailable, block rollover.
2. Transactionally acquire one operation lock in control, conditional on active ID/epoch/revision and no other operation. Freeze all relevant academic writes and roster/class-label edits during capture via server-enforced guards; compliant local clients must honor the same lock. Grade writes must update/check shared academic revision transactionally so read-before-lock updates cannot slip through. Do not rely on flushing this device to drain other devices.
3. Write a durable journal with caller-generated operation ID, expected epoch, source IDs/digests, target IDs and chunk completion. Snapshot under the lock; stage export labels/results and the next period. Source legacy paths are fenced for first adoption. Chunk idempotently by stable document IDs; verify complete manifest from server, counts, referential integrity, scores/results and decoded XLSX parity before publishing. A failed or partial stage is invisible to normal readers.
4. In one small final transaction verify lock ownership, source revision, complete manifests, expected active/epoch; mark old period sealed, new period active, set pointer/epoch and operation committed. Never clear grades first. On retry with the same operation ID return the existing result; a competing operation with an obsolete epoch is rejected, not a second new period. A double-click/reload must retain operation identity. Transaction timeout or unknown commit is resolved by reading the journal/control before any new attempt.
5. After acknowledgement refresh caches/selections by account/class/period/epoch and show the receipt. If interrupted before final commit, old pointer remains; resume deterministic staging or explicitly cancel and unlock after verifying the source. Lease expiry alone must not let a new writer bypass a still-running operation: takeover needs fencing token and CAS. Keep failed staging for diagnostics until reviewed cleanup. After final commit, do not roll pointer back if new grades exist; use forward repair and retain both histories.

For local parity use an owner/origin namespace, e.g. `gradebook_v2:U:C:control` and immutable versioned period blobs/chunks. Use a durable transactional local store for control/journal/payload commits and cross-tab locking, or explicitly restrict initial local rollover to a proven single-writer environment. Existing SharedPreferences multi-key queue is insufficient; do not claim crash atomicity. Restore/adoption cannot trust a newly signed-in U as owner of old unscoped keys. Device/origin/PWA storage availability must be surfaced; no implicit synchronization of local-only periods into cloud.

### Security, deletion and old clients

Rules must replace the broad recursive owner allow for academic/control paths with explicit grants: owner match; exact schema; validated class/period/item membership; immutable sealed descendants/labels/manifests; active pointer + epoch + operation fences; protected create/transition operations; no client archive deletes; no legacy academic writes after adoption. Direct SDK/REST attempts need emulator tests, including account B reusing account A's class/period/student IDs. Owner authentication alone does not protect archives from mistaken owner-client writes.

Hashes detect accidental corruption; they are not proof that an owner-controlled client copied every source document. Rules cannot practically recompute large manifests, hashes or grading results. Recommend a trusted rollover coordinator for cloud staging verification and final sealing, with clients requesting an owner-scoped idempotent operation and no direct seal/activation permission. Coordinator code, privileged access and rules must be separately approved and tested; privileged SDKs bypass rules and need their own owner/state checks. A client-only alternative must demonstrate equivalent bounded verification and transition guarantees before replacing this recommendation. No Cloud Function or privileged credential is introduced here.

Permanent class deletion must be rejected while a gradebook/control exists. Offer class soft archive/tombstone while preserving period navigation from the academic index and snapshot labels; keep retention/purge a separate explicitly approved operation. Never let recursive class cleanup, clearAll, roster deletion or undo reach sealed periods. Putting archives outside classes protects the path structurally but is not a substitute for these rules and UI guards.

Old clients cannot be made safe by a new-client-only feature flag. After adoption, deny their legacy academic writes at the server. They may display stale legacy grades and cannot edit the new active period. Require a version/update gate with clear save failures before enabling adoption; preserve legacy read access only if reviewed. Broad owner grants must be removed first. Local old clients cannot honor a new protocol, so supported-client/origin policy and multi-tab exclusion are release blockers. Freeze or explicitly bound any old-client roster/class-label changes during capture. No dual-write bridge: it can silently overwrite new history. Rollback to an old binary must never reopen legacy writes for an adopted class.

### Large classes

Current repositories submit whole unpaged lists/batches. A 1,000-student new period with 20 materialized score sets would be 20,000 score documents; avoid unnecessary full-mark rows where absent=100% is the frozen policy. Never put all scores or roster photos in one Firestore document. Use bounded chunks (proposed maximum 200 document writes, reduced for request bytes/rule-access budget), paginated reads, resumable journal and per-chunk integrity checks; keep final pointer transaction small. Measure actual limits against the pinned SDK/emulator and current Firebase documentation during implementation. The local 1,000-row fixture is not proof of cloud quota, performance or browser storage capacity. Set explicit supported class size/storage budget only after load testing and preserve partial work on quota/disk exhaustion.

## Backup and recovery runbook

This is a future operational procedure, not a command executed against production. XLSX is a teacher-readable companion, **not** a restorable backup: it omits raw assessments, null/missing distinctions, weights, timestamps and settings.

1. Before any adoption, freeze writes and record owner, class IDs, source commit/build, backend, device/origin, SDK/schema/policy versions, server acknowledgement and time. If offline writes cannot be drained, postpone. Do not collect access tokens in backups. Use approved encrypted storage/access and retention; agree operator and destination before handling actual records.
2. Create an authorized full raw database backup/export for the affected account's academic/class data, all nested scores/history/exams/categories/templates, roster and seating/room setup; explicitly enumerate children of orphan item documents. Separately back up local origin preferences and tool stores (key/type/value plus all canonical AND legacy keys, schedules, notes and settings). Include any period controls/journals/staging/sealed datasets. A Firestore export alone misses local settings; a Hosting rollback contains no data backup. Preserve a pre-change raw copy before running filtered model readers.
3. Produce a manifest of paths/keys/IDs, record counts by class/period/category/item/student, score absent/null/non-null counts, roster/class label digests, exam counts, raw file/chunk SHA-256 and schema versions. Validate duplicate IDs, dangling joins and ambiguous legacy ownership; quarantine/report ambiguity. Save decoded Excel cell/value/type evidence and calculated result map alongside raw backup. Check the copied backup's digest independently. No activation on mismatch or missing backup.
4. Rehearse restore **first** into a fresh isolated emulator/project or mock/local test origin, never over the source. Validate owner mapping without reassignment, exact keys/types and all counts/digests/relationships. Recompute using pinned policy and compare materialized historical results and decoded XLSX cells/types/labels; preserve null/missing/inactive behavior. Exercise absent students, changed names/weights/maxima, old-term exams, collision IDs across accounts, interrupted import, disk/quota failure and duplicate restore. Duplicate restore must not create additional periods. Measure restore duration and document achievable recovery time; no RTO is claimed by this PR.
5. Before final commit: failed parity, incomplete manifest, stale revisions, lost lock, unidentified ownership, unacknowledged writes or failed restore rehearsal means HOLD. Keep original pointer/source, block writes as appropriate, and resume/cancel via journal. After activation: seal violations, unexplained grade changes or export mismatch means disable further rollover/adoption and preserve all new writes; collect operation evidence and repair forward. Do not restore a pre-rollover backup over valid later grades. A human-approved point-in-time restore must reconcile subsequent operations in isolation first.
6. Restore is not complete until independent re-read verification passes for raw counts/digests, historical calculation, all Excel variants, live roster/settings/seating/schedule preservation and account isolation. Record operator, source/target, scope, timestamps, hashes, validation report and release receipt. No production recovery or migration tooling is supplied here.

The executable fixture rehearsed JSON backup→mock-store clear→restore with exact key/value equality, explicit null and roster/term checks. This establishes required backup content, not actual Firestore disaster recovery, origin persistence, encryption, SHA verification or operational recovery time.

No design can reconstruct grades, labels or prior calculation policies already overwritten before adoption. Preserve all available source evidence and report that historical completeness limit rather than inventing periods from the current term field.
